# nano_sdr_pluto_ofdm_tx7020 — OFDM PHY TX на платі Pluto з Zynq-7020 (LVDS)

Передавач dual-mode OFDM PHY (`../nano_sdr_pluto_ofdm/rtl`, v0.8.0) для плати з проєкту `projects/pluto`
гілки `docs/pluto-runtime-bitstream-jtag` (коміт d206de1f9): xc7z020clg400-2, AD9363 через LVDS.

## Що змінено відносно `projects/pluto`

| | `projects/pluto` | цей проєкт |
|---|---|---|
| TX-тракт | DAC DMA (циклічний) → upack → інтерполятор → DAC | DAC DMA (не циклічний, 64-біт stream) → `phy_tx` → DAC канал 0 |
| Регістри PHY | — | `0x7C440000` (`phy_regs_axil`, ID `OFTX`) |
| RX-тракт | decimator → cpack → ADC DMA | без змін (щоб працював штатний device tree) |
| ILA | `rx_debug_ila` | прибрано |
| Тактовий констрейнт `rx_clk` | 4 нс | 4 нс як у штатному; шляхи PHY мають 2 такти (multicycle), бо PHY працює лише на 30.72 МС/с (`l_clk` 122.88 МГц). З 8 нс драйвер не калібрував LVDS на 61.44 МС/с і передавач видавав сміття |

Адреси `axi_ad9361` (`0x79020000`) і DMA (`0x7C400000`, `0x7C420000`) ті самі, що у штатному дизайні, тому після
заливки бітстріму через JTAG штатний Linux і його драйвери працюють далі.

## Збірка

```
build_vivado.bat                      (Vivado 2025.2, ≈ 1 год)
vivado -mode batch -source post_reports.tcl     (звіти таймінгу й ресурсів)
```
Бітстрім: `nano_sdr_pluto_ofdm_tx7020.runs/impl_1/system_top.bit` (стиснений).

## Запуск на платі (метод з `README_runtime_bitstream.md`: JTAG, до перезавантаження)

Кроки 2–5 одним скриптом (PowerShell, з цієї папки): `.ringup.ps1` (з `-SkipProgram`, якщо бітстрім уже залито).
Пароль плати (`analog`) скрипт підставляє сам. Передача з живим виводом: `.	x.ps1` (параметри `-Mode`, `-Gain`,
`-Seconds`, `-Extra`), логи після зупинки копіюються в `.\logs\`. Нижче те саме вручну.

1. Плата завантажена зі штатною прошивкою, `ssh root@192.168.2.1` працює, JTAG-адаптер під'єднано.
2. Залити бітстрім:
   ```
   C:\AMDDesignTools\2025.2\Vivado\bin\xsdb.bat program_pl_jtag.tcl
   ```
   Скрипт лише заливає PL. Що в PL саме цей бітстрім, перевіряє крок 5 (`plutolink diag` показує `PHY ID OFTX`).
3. Перезавантажити драйвери AD9361:
   ```
   ssh root@192.168.2.1 "modprobe -r cf_axi_dds cf_axi_adc ad9361_drv ad9361 2>/dev/null; sleep 1; modprobe ad9361; sleep 2; ls /sys/bus/iio/devices/"
   ```
4. Скопіювати програму (статичний ARM-бінарник, `../nano_sdr_pluto_ofdm/sw/plutolink/plutolink`):
   ```
   scp ../nano_sdr_pluto_ofdm/sw/plutolink/plutolink root@192.168.2.1:/tmp/
   ```
5. Перевірка:
   ```
   ssh root@192.168.2.1 /tmp/plutolink diag
   ```
   Очікується `PHY ID OFTX`, частота `l_clk` і темп відліків ЦАП близько 30.72 МС/с. Якщо `UNKNOWN`, у PL не той бітстрім;
   якщо знімок регістрів не встигає, немає `l_clk` (драйвер AD9361 не налаштував інтерфейс).
6. Передача (спершу кабель і 30–60 дБ атенюації, див. `sw/plutolink/README.md`):
   ```
   /tmp/plutolink tx --freq 2450e6 --nsyms 2 --mode 0 --gain -60 --rate 200 --log run1
   ```
   `--mode 0` = MAX RANGE (QPSK, LDPC 1/2), `--mode 1` = MAX RATE (16-QAM, LDPC 5/6). Кожну секунду друкуються лічильники PHY
   (прийняті / відтворені пакети, переповнення, темп ЦАП), наприкінці кількість пакетів і швидкість payload.

## Як перевірити передавач без другого PHY

Друга плата зі штатною прошивкою, налаштована на 30.72 МС/с і ту саму частоту, записує IQ першого каналу
(`iio_readdev -b 1048576 -s 30720000 cf-ad9361-lpc voltage0 voltage1 > cap.iq`, int16 I/Q). Запис розкодовує
Python-приймач фреймворку `phy_sim`:
```
cd ../nano_sdr_pluto_ofdm/phy_sim
python -m phy_sim.cli replay path/to/cap.iq --out results/hw_cap1
```
Поруч із `cap.iq` покладіть `metadata.json` з параметрами передавача, інакше приймач візьме типові:
```
{"config": {"payload": {"nsyms": 2}, "phy": {"mode": "max_range"}}}
```
Що це покаже: чи кадри виявляються, як сходиться LDPC, EVM, CFO. Чого не покаже: BER проти переданих даних, бо replay
порівнює з власною тестовою послідовністю, а не з PRBS програми `plutolink`. Так видно, чи передавач видає правильні
кадри, ще до порту приймача в PL. Приймач у PL для цієї
плати (`nano_sdr_pluto_ofdm_rx` під LVDS) ще не портовано.

## Не перевірено

Нічого з цього не запускалось на залізі. Зокрема: чи штатний драйвер `cf-ad9361-dds-core-lpc` без змін віддає буфер у
не циклічний DMA (на Nano SDR Pluto для цього був свій device tree), і чи плата працює в 1R1T чи 2R2T (PHY працює в обох,
використовується канал 0).

## Дві плати: A передає, B записує

Обидві плати за замовчуванням мають адресу 192.168.2.1, тому одну треба перевести в іншу підмережу. На платі B (та, що
записує) відкрийте диск `PlutoSDR`, у `config.txt` змініть
```
ipaddr = 192.168.3.1
ipaddr_host = 192.168.3.10
```
збережіть, виконайте Eject диска і дочекайтесь перезавантаження. Плата A лишається на 192.168.2.1.

Плата B працює зі штатною прошивкою (штатний бітстрім, приймач у PL не потрібен). Порядок:
```
.\bringup.ps1                  # плата A: наш бітстрім, драйвери, plutolink
.\link_test.ps1                # A передає, B записує 2 M відліків, ПК розкодовує
```
`link_test.ps1` запускає передачу на A у фоні, записує IQ на B (`iio_readdev`, 30.72 МС/с, ручне підсилення `-RxGain`),
копіює запис у `.\logs\` і розкодовує його `phy_sim/experiments/decode_capture.py`: на кожен пакет MODE_ID із заголовка,
результат LDPC, SNR каналу, CFO і чи цілі корисні дані plutolink (CRC32). Параметри: `-Mode`, `-Nsyms`, `-Gain`, `-RxGain`,
`-Freq`, `-Samples`, `-TxIp`, `-RxIp`.

## Перший результат на залізі (2026-10-22)

* Цифрова петля AD9363 (`/sys/kernel/debug/iio/iio:device0/loopback = 1`) на платі A: усі пакети розкодовано, SNR 48 дБ,
  дані `plutolink` цілі. Цифровий тракт програма → DMA → PHY → LVDS → AD9363 працює.
* Через ефір (антени поруч, плата A послаблення 0 дБ, плата B підсилення 40 дБ, 2450 МГц, MAX RANGE, 2 символи):
  23 пакети наші за 32.6 мс запису, 14 з них з цілими даними (CRC32), SNR каналу ≈ 3 дБ, CFO ≈ −220 Гц.
  Сигнал на межі чутливості MAX RANGE: OFDM-пакети на ≈ 14 дБ слабші за тестовий тон через запас під піки, а при
  послабленні −10 дБ і слабше вони лежать на рівні шуму. Для стабільного прийому потрібно більше рівня (ближче антени,
  кабель з атенюатором, вищий цифровий рівень PHY).

## Передача картинки (2026-10-22)

```
.\link_test.ps1 -Gain 0 -RxGain 40 -Nsyms 4 -Samples 6000000 -File .\test_image.png -Name img2
```
`plutolink tx --file` ріже файл на шматки (504 байти при 4 символах MAX RANGE), номер шматка в заголовку пакета, кожен пакет
з CRC32; передача циклічна. `phy_sim/experiments/image_rx.py` збирає файл з пакетів з цілим CRC і порівнює з оригіналом.
Результат: 125 пакетів у записі 195 мс, 61 цілий, усі 8 шматків є, `logs/img2_received.png` побайтово збігається з
`test_image.png` (MD5 48105418…). Передавач: 933 пакети/с, 4.0 Мбіт/с корисних даних.

## Променеформування (ТЗ 006, з v0.10.0)

Бітстрім будується з `phy_tx_axis_top` `BF = 1`: два канали ЦАП (TX1, TX2) з вагами по піднесучих, вихідним NCO, трекером затримки,
спільним часом EPOCH і шиною JP5 між платами (опис регістрів у шапці `../nano_sdr_pluto_ofdm/rtl/tx/phy_tx_axis_top.v`).
Пакети без прапорців (як від `plutolink`) ідуть лише на TX1, як і раніше (маска за замовчуванням `cfg2[3:2] = 01`).
Програма плат: `../nano_sdr_pluto_ofdm/sw/beamd` (README там).

### Шина JP5 між A1 і A2: складання

JP5 (2×10, крок 2.54 мм) на платі не запаяний. З'єднуються лише 6 контактів, дріт до дроту між двома платами, довжина до 30 см:

| JP5 | Мережа | FPGA | Сигнал | Напрямок |
|---|---|---|---|---|
| 7 | `3V3_IO1` | V10 | EPOCH | A1 → A2 |
| 9 | `3V3_IO2` | U9 | SCLK | A1 → A2 |
| 11 | `3V3_IO3` | U10 | MOSI | A1 → A2 |
| 13 | `3V3_IO4` | T9 | UP | A2 → A1 |
| 2, 20 | GND | | земля | |

Послідовні резистори 33 Ом на виходах A1 (контакти 7, 9, 11) біля A1. Підтяжки вже ввімкнені в FPGA (`PULLUP` у
`system_constr.xdc`), окремі резистори не потрібні. **Не з'єднувати** контакти 1, 3, 5 (живлення 5 / 3.3 / 1.8 В), 15 (`XTAL_VTC`),
17 (`PTT`), 19 (`AD936X_SYNC`) і лінії `1V8_*`; стрічковий кабель 1:1 не використовувати.

Перед першим з'єднанням:
1. Знайти контакт 1 (квадратна площадка) і прозвонити: контакти 2 і 20 дзвоняться на землю плати.
2. Прозвонити дроти: жоден не торкається контактів 1, 3, 5.
3. Увімкнути кожну плату окремо з бітстрімом BF: на контактах 7, 9, 11, 13 має бути 3.3 В (підтяжка, роль 0 = усі входи) або 0 В.
4. Лише тоді з'єднати плати.

### Перший запуск (M1: одна плата, два канали)

Плата A з антенами на TX1 і TX2 (або дільник/суматор і атенюатор до B), плата B (штатна прошивка, 192.168.3.1) з антеною на RX1:
```
.\bf_m1.ps1                 # заливка BF-бітстріму на A, релей на ПК, три прогони по 30 с (лише TX1 / TX1+TX2 без ваг / з вагами), звіт
```
Звіт (`bf_m1_report.py`) рахує виграш пакета даних на B відносно TX1 і порівнює з ідеальним для виміряних амплітуд каналів.

### Дві плати (M2 / M3)

A1: `beamd leader`, A2: `beamd follower`, B: `beamd anchor` (4 антени), ПК: `python bf_relay.py`. Бітстрім BF на обох A.

## Continuous (потоковий) режим і швидкість (v0.10.1)

Пакетний режим (за замовчуванням): кадр ≤ 8 символів, пауза між кадрами; continuous: довгий кадр до 255 символів без паузи.
```
.\link_test.ps1 -Freq 1400000000 -Mode 1 -Nsyms 64 -TxExtra "--cont --gap 0" -Rate 0 -Gain -10 -RxGain 40 -Samples 3000000 -File .	est_data_100k.bin -Name cont1
.\link_test.ps1 -Freq 1400000000 -Mode 1 -Nsyms 8 -TxExtra "--gap 12000" -Rate 0 -Gain -10 -RxGain 40 -Samples 6000000 -File .	est_image.png -Name f1400
```
`test_data_100k.bin` — 100000 випадкових байт (seed 7: `random.seed(7)`, `bytes(random.getrandbits(8) ...)`, файл не комітиться, `*.bin` в ignore).
Результати (кабель TX1 → 30 дБ → RX1): пакетний MAX RATE 8 символів 23.2 Мбіт/с (157/157 цілих на 1.4 ГГц, 119/156 на 2.45 ГГц через завади Wi-Fi),
continuous MAX RATE 64 символи 47.9 Мбіт/с (19/19, файл 100 КБ ідентичний). Повна таблиця і висновки: `../nano_sdr_pluto_ofdm/STATUS.md` (v0.10.1).
Рівні для кабелю з 30 дБ: TX −10 дБ, RX 40 дБ (TX −20 / RX 20 дає лише шум). Якщо плата A після заливки бітстріму не відповідає на
192.168.2.1, перевірте `config.txt` (перший рядок `[NETWORK]`) і перезапустіть живлення.
